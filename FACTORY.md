# The factory

A six-seat software factory that runs in one Band Desktop room per run. For each stage, one task is posted into the room: that message is the only human input. The seats turn it into a working, verified, packaged stage and end it with a final report; nobody outside the band answers a question, approves, accepts or rejects anything. Every seat is a headless Claude Code runtime that Band Desktop starts on demand, with a generic mandate as its owner instructions and nothing else from the machine it runs on. Another team can stand it up from the six files in `mandates/`, the scripts in `factory/` and the steps under "Stand it up". Track detail lives only in the task text posted into the room (template at the end), never in a mandate.

## In two minutes

- **What it is:** six Claude Code seats in one Band Desktop room, each owning one kind of artefact; the task message for each stage is the only human input.
- **What it produced:** the second full run delivered all four stages. On the organizers' harness in isolated mode each stage folder claims its own stage, and `stage-4/` passes every shipped check of suites 1 to 4. Task to final report: 3 h 51 min, 5 h 46 min, 5 h 17 min and 8 h 46 min; the room holds 3,260 messages; the only human input was the four task messages.
- **What it caught:** in the submitted run the critic blocked 8 plan versions, the verifier refuted 3 items and reopened a delivered stage that missed a time limit, and the clerk caught a stage folder shipped with the previous stage's run instructions; every catch is in `room.json` and `EVIDENCE.md`. In the first full run the designer also rejected a screen the verifier had passed, and the clerk showed that a stand-in build falsely claims the next stage ("How the factory catches and recovers from bad work").
- **What it cost:** the first full run's seats used $127 to $212 of API-price-equivalent tokens per completed stage, about 4 to 7 % of one Max plan's weekly limit; the second run's seats used $88 to $168 per stage, $513 for all four (18.5 % of one Max plan's weekly limit).
- **What failed, and the fix:** the first full run's room stopped at 10,000 messages in stage 4, 78 % of them tool-call copies; the second run keeps four seats' tool activity out of the room and used 3,260 messages for four stages.

## The seats

| Seat | Owns (the one thing it writes) | Model, effort | Room activity |
|---|---|---|---|
| architect | the plan with its requirements list, the board and its states, scope, every DECIDED point, the foundation design brief, the done verdict, the stage's final report | `claude-opus-5-5`, xhigh | off |
| critic | the verdict on every plan and re-plan (CLEAR, BLOCKED, SPLIT) and a blind answer to the foundation design brief | `claude-opus-5-5`, xhigh | off |
| designer | the design system file and the look verdict on every change to a screen (APPROVED, CHANGES, UNVERIFIED) | `claude-opus-5-5`, xhigh | tools |
| builder | product code, one commit per concern, each handoff with evidence and a known-bad probe | `claude-opus-5-5`, high | tools |
| verifier | the spec-derived acceptance checks and the verdict on every handoff, reproduced in its own clean checkout | `claude-opus-5-5`, xhigh | off |
| release clerk | the clean-environment recipe, the delivery layout, the two release gates, the reverse check, the evidence record | `claude-opus-5-5`, high | off |

"Room activity" is Band's per-agent setting for copying a seat's work into the room: `off` copies nothing, `tools` copies every tool call and its result. Band states that a seat's replies, permission asks and turn lines post whatever the setting; a scratch-room check on 2026-09-29 confirmed it for replies (VERIFIED: a seat set to `off` ran two commands and posted only its reply; a seat set to `tools` posted two lines per call). Why these settings: "Why these choices".

The four answers Band's hacker guide (band.ai/hacker-guide) asks a crew to state:
- **The crew:** architect, critic, designer, builder, verifier, release clerk. The human posts each stage's task and does nothing else in the room.
- **Who mentions whom, and who is deliberately left out:** the task mentions the architect; the architect mentions one seat per request; the critic, designer, builder, verifier and release clerk mention only the architect. Nobody but the architect mentions the builder, so it never receives two instructions at once; nobody but the architect asks the critic, the verifier or the designer for a verdict, so no verdict is requested by the seat whose work it judges.
- **The typical flow in one line:** task in, requirements list built from the specification, foundation design answered twice (the critic blind) and reconciled, plan cleared by the critic, design system committed by the designer, items built one after another while earlier ones are verified, each reproduced by the verifier against its own spec-derived checks and, for screens, reviewed by the designer at the same time, repeated, packaged, gated and reverse-checked by the clerk, final report.
- **What breaks without the room:** the board is the state of record for every seat's on-wake rule, the mentions are the only routing, and three verdicts stop work in the room itself: the critic's BLOCKED stops a plan, the verifier's REFUTED and the designer's CHANGES stop an item (the guide's "blockable verdicts"); the builder's next step depends on what they found (its "dependent handoffs").

## The loop

The mandates say "unit": the smallest set of items the task grades or delivers together. On this track every unit is a stage.

1. **Task in.** The stage's task is posted into the room addressed to the architect: the stage's specification pasted verbatim, the absolute paths (result repository, stage folder, acceptance-check folder, the organizers' package), the harness commands, the runtime limits, the room's message limits, the later stages' specifications for reference, and for a stage with screens the design direction. It is the only human input for the stage. Before its first handoff the architect confirms that every seat it will address is in the room's participant list, and re-adds a seat a handoff reports absent.
2. **Requirements list.** Before planning, the architect turns the specification text into a numbered requirements list: every rule, state, response, error, boundary, limit and screen, quoted, one line each, with the item that covers it. Only part of each stage's checks ship with the task (between 11 and 83 % per stage on the track we ran) and every held-back check is written from the specification, so code written to the shipped checks is incomplete. The specification is the requirement; the provided checks are a sample of it.
3. **Foundation decision (once per task).** Before the first plan, the architect sends the critic a design brief: how data is stored, how simultaneous or repeated requests are kept from interfering, how later stages extend the design, with the complete task text and no recommendation. The critic answers before it opens the plan. Where the two answers differ on something the requirements depend on, the verdict is SPLIT; the architect answers once; a second SPLIT is settled by rule, never by preference or by asking anyone: the reading that keeps more lines of the requirements list satisfiable wins, and on a tie the critic's. The outcome is recorded in the plan as DECIDED, "two-seat" or "two-seat, split settled by rule", and is not re-opened without a new line of the task or a new check result.
4. **Plan and review.** The architect publishes the room plan (numbered items grouped into units, each with one acceptance line: a command from a clean checkout and its expected output, and the requirement lines it covers) and the board. No item of a plan or re-plan is assigned before the critic's CLEAR. The critic blocks a plan that leaves a requirement line or a provided check without an item, an acceptance line that is prose, work built to a later stage's behaviour, or a claimed property under simultaneous or repeated execution without an item that proves it and a known-bad that would show it failing. Two planning rules came out of the critic's blocks in the first run: every new way of writing stored data is exercised at the same time as every existing writer, and every rule that applies across operations is proved on every operation that exists at the end of the unit. A second BLOCKED on the same finding is settled like a second SPLIT.
5. **Design (stages with screens).** Before the first screen item, the architect sends the designer the task's screens, states, layout and visual direction in full. The designer commits one design system file: tokens, type scale, spacing, focus style, breakpoints, component rules and a layout note per screen and state. With no direction in the task it first drafts at least three different directions and renders each; when the task carries a direction (ours did, see "Why these choices") it works within it, and the task text says the specification wins on any difference. Screen items are assigned only after that commit and name it.
6. **Build.** The architect asks the release clerk for the clean-environment recipe at the start; it is published in the plan before the first verification. The architect assigns one item at a time with the complete task text, and assigns the next item as soon as the builder hands the current one off: the builder builds it on top of the handed-off commit, so building and verifying overlap. A refuted item goes back to the builder ahead of everything else, and the fix is carried into any later item before that item's handoff. The builder runs the existing checks on the clean state first, implements the smallest change that satisfies the item's requirement lines, commits only the paths it owns under its own seat name, and hands back an evidence block: files, full commit id, exact commands and output, what is not covered, and one known-bad probe showing the new behaviour's check can fail for the reason under test. A departure from a DECIDED point is asked about before it is built, never announced in a handoff. During work longer than 45 minutes it posts a progress line every 45 minutes.
7. **Verify.** The verifier obtains the commit in its own clean directory; reruns the provided checks of this unit and of every earlier unit; writes its own acceptance checks from the specification (not from the builder's code) for the requirements the item touches, each calibrated against a known-bad before it is trusted, and commits only that path; reads the diff and the test bodies; for a property under simultaneous or repeated execution, removes the protection in a throwaway checkout and runs the operation simultaneously and repeatedly (the check must turn red); runs timing and load checks alone, with nothing else of its own running; for a screen, checks that the whole screen agrees with the server after the action, not only the element the item changed; and returns VERIFIED, REFUTED or UNVERIFIED with commands and output. Its full acceptance set runs at the repeat (step 9).
8. **Look review (items that change a screen).** Requested together with the verification, on the same commit. The designer serves the commit from a clean checkout with outbound network disabled, captures every changed screen at the narrowest required width, a middle width and a desktop width in every named state (including the state after a failed or uncertain action) with a headless browser, and returns APPROVED, CHANGES (each change with the screen, width, state, broken rule and the screenshot path) or UNVERIFIED. Only VERIFIED plus, for a screen item, APPROVED moves a board task to verified. A CHANGES verdict counts as a refutation, and so does a builder's stop after three focused attempts on a check that stays red. An item refuted twice is not patched a third time: it is re-planned with a genuinely different approach and the re-plan goes back to the critic. A non-blocking note from the verifier or the designer becomes an item only when a requirement line requires it (a look note about a quality the task's own words require counts); otherwise it goes to "Not doing" or the next unit.
9. **Repeat.** When a unit has checks that involve simultaneous or repeated execution, the verifier repeats them, with its full acceptance set, from a fresh clean checkout of the commit to package, because a race can pass once and fail on a later run.
10. **Package.** The release clerk builds from a clean checkout of the named commit, assembles the stage folder the task prescribes (ours: `Dockerfile`, `RUN.md`, source, no nested `.git`), exercises its two release gates (the clerk's own, not the organizers' gates 1 to 4): gate 1 (build, then start with outbound network disabled within the runtime limits and complete a first unit of work) and gate 2 (no credentials, private data or unrelated files), runs the organizers' structure check, and runs the reverse check: the next stage's provided checks must not all pass on this stage's folder (a folder that passes the next stage's whole suite earns nothing for its own stage). Each gate is PASS, FAIL or UNRUNNABLE with the reason; every PASS rests on a negative control that fails for the reason the gate tests. The clerk's environment recipe gives each seat its own range of host ports and its own container-name prefix, so seats working at the same time never collide.
11. **Final report.** On gates that are PASS or UNRUNNABLE, the architect moves the stage's tasks to done and posts the final report: the items with verdicts and commits, both gates (naming any UNRUNNABLE gate and its reason), the reverse check, the requirements coverage (lines covered, lines not covered and why), the measured wall-clock time, the count of each verdict taken from the plan's record, what each rejection changed, and what the stage does not cover. The final report ends the stage; no seat asks anyone to accept it. The next stage's task arrives after it and works on its own copy of the delivered folder.

Three properties make the loop transferable: a report is never evidence (every claim carries a command and its output another seat can reproduce); every check is calibrated by a known-bad before it is trusted, including the plan (the critic), the acceptance checks (the verifier's calibration) and the no-network gate (a negative control); and each artefact has exactly one writer, so seats never overwrite each other. The board and the git log are the state of record: every mandate has an on-wake rule that reconciles the seat's memory to them.

In the first run the verifier's acceptance suites grew with the product: 747 checks at stage 1, 1,186 at stage 2, and a full run of 1,659 passing at stage 3, each calibrated on a known-bad, against provided suites of 120, 25 and 7 checks. ## Runtime and quota

Generic: seats run on whatever Claude Code sign-in the clean folder holds, or on any other runtime Band supports. Seats run only while a message is being handled, so spend tracks the work, not the clock. The stand-up script refuses any model that its runtime would bill outside the subscription when run headless (for this team, Anthropic's Fable-class models: a headless request bills usage credits without a prompt).

This team: all six seats on one Claude Max subscription, shared with other work the same week. The operator checks the subscription's weekly meter before posting each stage and holds the next stage (never a running one) if it would run out; nothing is lost while waiting, because state lives on the board and in git.

## Why these choices

- **One model for all six.** Every seat's output is either the judged result or a gate on it. The practice runs showed what a weaker seat costs: a Sonnet-class release clerk reported a false no-network PASS that only an outside known-bad caught, and a Sonnet-class builder fabricated one probe output and retracted it. Efforts differ by the kind of reasoning: the seats that judge (architect, critic, designer, verifier) run at the top of the band. Each seat is created with the exact model id and effort, and both are visible in the spawned process's command line (`--model claude-opus-5-5 --effort xhigh`, VERIFIED 2026-09-26). When a faster, cheaper sibling model appeared during the event we kept all six on one model: its cost per finished task was not lower on the public benchmark we checked, and the seat it would most likely replace, the release clerk, is the one whose false PASS we had already seen.
- **A designer seat.** Half of the application score is a UI that is coherent, presentation-ready, responsive and clear in every state the specification names. In our preparation, a single agent asked for "a good look" produced a clean, restrained and entirely generic screen, which the human rejected on sight. For the judged runs the human chose the direction before the run, from four directions the preparation had rendered, and it is part of the task text (fonts, palette, a signature element, reference pictures); the designer turns it into a design system and owns every screen-level decision and every look verdict. Its mandate still requires three rendered directions when a task carries none.
- **The critic answers the foundation question blind.** The costliest decision of a multi-stage task is made once, at the start. Two independent answers, one of them written before the plan is seen, expose the choices one seat would not question; a disagreement is settled by a rule that favours the requirements, never by rank.
- **Every check is calibrated.** A check that has never been seen to fail is not evidence. The first practice run had a provided concurrency check that stayed green on a known-bad; that is why the verifier writes and calibrates its own checks and the clerk puts a negative control behind every PASS.
- **One writer per artefact.** Each file in the repository has one owning seat (code: builder; acceptance checks: verifier; design system: designer; evidence record: clerk; plan and board: architect), so seats never merge each other's work and the git log shows who did what (author name = seat).
- **A room that fits the whole run.** Our first full run's room stopped at 10,000 messages in stage 4, and 78 % of its 10,005 messages were tool-call copies (failure 10, which also has Band's later fix to its limits). A small room is easier to read and to judge whatever the limit is, so four seats now copy nothing into the room; the builder and the designer copy their tool calls, so a reader of the room still sees the code being written and the screens being captured; every seat chains a routine into one command instead of many small calls; handoffs go in as few parts as the room's 23,000-character message size allows; and the operator's watcher reports the count at 3,000, 5,000, 7,000, 8,000 and 9,000 messages. Projected from the first run: about 5,400 messages for four full stages (DERIVED: the first run's builder and designer tool lines plus all its non-tool lines, scaled from 3.5 to 4 stages); the second run used 3,260. The organizers score teamwork from the room log and the git history, and state they do not score chat volume.
- **Build and verify at the same time.** In the first run the builder had no active item for 61 % of the wall-clock time, because each item waited for the previous verdict. The builder now builds the next item on top of the handed-off commit while the verifier and the designer work on the previous one; a refutation jumps the queue.

## How a run stays hands-off

The event's rule is that the posted task is the only human input: no approvals, hints, reruns or "looks good, continue". Everything a human used to settle is settled inside the band, and everything that used to stall a run is closed by a rule or a mechanism:

- **Open questions:** the architect answers every question a seat raises; where the task does not settle it, it decides, writes DECIDED with the reason and what would change it into the plan, and moves on. A self-contradicting task: the reading that keeps more requirements satisfiable.
- **Disagreement between seats:** a second SPLIT or a second BLOCKED on the same finding is settled by the rule in step 3 and recorded in the plan.
- **What the band cannot fix:** an environment nobody in the band can repair, or a requirement no approach satisfies after a re-plan, is recorded with its evidence in the plan and the final report. No seat waits for someone outside the band.
- **Silent seats:** Band wakes a seat only when it is mentioned, so a seat that stops talking wakes nobody. The builder, the verifier and the release clerk post a progress line every 45 minutes of long work, and the architect, on every wake, reads the time, the board and its latest messages in one command and re-sends once any handoff with no reply and no progress for 60 minutes, then reassigns or records the stalled seat.
- **Split messages:** a handoff too long for one message is numbered "part k of n"; the earlier parts carry the pasted task and say "context, no action yet", the request is in the last part, and a seat acts only when part n of n has arrived.
- **Stale and repeated requests:** a request posted before the task a seat is working on, or about an item the board shows verified or done, is settled with no reply and no work; a repeated request gets the earlier answer, not new work, so a re-send never doubles the work. Crossed messages are normal: a seat leads with the blocking point and restates the current state instead of re-arguing.
- **Lost replies:** after posting a verdict, report or handoff, a seat confirms it appears in the room's message list and posts it once more if not (failure 5).
- **Background commands:** no seat runs a command in the background. This is enforced, not only asked: the seat launcher sets `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` and long Bash timeouts (20 minutes default, 60 maximum), and a known-bad showed the Bash tool refusing a background run with the variable set and accepting it without (VERIFIED 2026-09-26).
- **A shared machine:** no seat stops, restarts, removes or changes a container, process, service or port binding it did not start in this run, and it stops its own by the process id or exact container name it recorded; it works around what it finds.
- **Permission prompts:** seats run in Claude Code's `auto` permission mode, which asks only before risky commands; the organizers answered at the kickoff Q&A (2026-09-26) that approving a permission prompt is not human input. Seats are told never to run a command that needs a permission decision from outside the band (use a new scratch folder instead, or record the blocker).

## Routing, attention and who the human is

- Band rooms route by mention: only a mentioned agent sees and processes a message. Every seat therefore ends every piece of work with a message that mentions the architect, and every handoff carries the complete task text pasted in full, because a seat that is pointed at "the room" or an earlier message cannot see it.
- One room per run. A development run may be steered; a judged run is a fresh room and a fresh result repository.
- The human's role in a judged run: create the room, add the six seats, post each stage's task after the previous stage's final report. On this team a supervising Claude Code session on the human's machine carried out these steps on his instruction: it created the room in Band Desktop, added the seats, posted each stage's prepared task under his name word for word, and watched the room read-only for milestones, permission prompts and the message count. It sent nothing else into the room. The stage tasks were prepared before the run; the only human choice in them is the design direction.

## Stand it up

Prerequisites (what this team ran, on Windows 11):
- Band Desktop (0.4.10) and a Band account; it installs the `jam` CLI, and `jam preflight` must show its daemon running.
- Claude Code 2.1.280 or newer on the same machine (`claude --version`), signed in to the model access the seats will use.
- Git, a running Docker daemon, and Python 3.12+ with the organizers' harness installed as their guide's "Prepare" section describes (a venv with `harness/requirements.txt` and Playwright's Chromium). The guide runs these inside WSL2 on Windows; we used a native Windows venv, which needed one local change: in `harness/cli.py`, isolated mode passes the test path as `path.relative_to(ROOT).as_posix()` instead of `str(...)`, so a Windows path reaches the Linux check container in POSIX form.
- An empty result repository (`git init -b main <path>`) holding `README.md`, this file, `mandates/` and `factory/` as its first commit.

1. **A clean configuration folder for the seats.** Create an empty folder and sign Claude Code in once inside it: `CLAUDE_CONFIG_DIR=<seat-config-folder> claude auth login` (PowerShell: `$env:CLAUDE_CONFIG_DIR = '<seat-config-folder>'; claude auth login`). The seats are spawned through launchers that point `CLAUDE_CONFIG_DIR` at this folder, so the machine's personal CLAUDE.md, rules, hooks, skills, agent types and plugins never reach them (VERIFIED 2026-09-26 on the seats' own transcripts). Band's room tools are injected by Band Desktop at spawn.
2. **Seats.** Run `factory/standup-test.ps1 -Workspace <workspace>` (the script's own known-bads; every check must PASS or SKIP, and the skipped ones need a live or stopped seat set, a signed-in seat folder or an off-quota builder wrapper), then `factory/standup.ps1 -Workspace <workspace> -MandateDir <repo>\mandates -SeatConfigDir <seat-config-folder> -PlainNames`, first with `-DryRun`. The script checks `jam preflight` and the Claude Code version, refuses a seat folder that is not signed in, writes one launcher per seat (it sets that seat's git author and committer name, plus the background and timeout variables above), writes a generic workspace `CLAUDE.md` and a `.claude/settings.local.json` as a second layer, creates the six seats with `jam agent create` (transport `claude-code-cli`, exact model and effort, permission mode `auto`), attaches each mandate with `jam agent instructions set` (live-linked, so point it at the committed mandates; Jam on Windows accepts the path only with forward slashes, and the script passes it that way), and requires every seat to show `Connected running=true`. `-PlainNames` names each seat after its role, so the room shows "architect" and the mandate file `mandates/architect.md` matches it. On macOS or Linux the same steps are `SEAT_CONFIG_DIR=<seat-config-folder> factory/standup.sh <workspace> <repo>/mandates --plain-names` (first with `--dry-run`); this team ran the PowerShell script, and the bash twin was checked with a dry run and a launcher test, not a whole run. A Band account holds at most 20 agents (VERIFIED 2026-09-26); delete seat sets you no longer use.
3. **Room activity.** In Band Desktop, for each seat: Agents, the seat, Runtime tab, "Room activity feed": `off` for the architect, critic, verifier and release clerk, `tools` for the builder and the designer (Band's default copies everything, reasoning included). We found no CLI flag for it in 0.4.10. Check it before a judged run: one message in a scratch room to a seat set to `off` and one set to `tools`; the first must post its reply and no tool lines.
4. **Room.** In Band Desktop create the room and add the six seats (Participants, +). A seat whose worker is stopped is started from its Runtime tab ("Restart agent"). Then run `factory/standup.ps1 -Workspace <workspace> -Prefix <the prefix step 2 printed> -PlainNames -RoomId <room id> -RoomCheckOnly`: it waits until every seat shows a `default-<room id>` session, because a seat without that session never hears the task.
5. **Task.** Post each stage's task addressed to the architect, pasted in Band Desktop or from a shell as `jam room send <room id> "$(cat task.txt)" --mention <the architect's participant id from jam room participants>`. A 23,614-character task was stored whole, byte for byte (VERIFIED 2026-09-29); read the stored message back and compare it with the file (on Windows, read `jam`'s JSON output as UTF-8, or the comparison fails on the first dash).
6. **During the run.** Nothing in the room. Post the next stage's task after each final report. To watch without touching the room: `python -u factory/stage-watch.py <room id> <owner handle> <owner participant id> none 45 1680 20 <transcript folder>` (the transcript folder is `projects/<the workspace path, separators turned into dashes>` inside the seats' clean configuration folder) prints milestone messages (verdicts, reports, handoffs, anything addressed to the owner), errors, pending permission prompts (a seat blocked on a prompt posts nothing), quiet spells and the room's message count at 3,000 to 9,000; it exits after 28 minutes and prints the stamp to resume from.
7. **After the run.** Open the room in the Band console (Band Desktop, the room's menu, "Open in Band"), then the room's menu, Download, "Download full session", and save the file unchanged as `room.json` at the repository root. Check it before you commit it: its message count and its first message (the seats joining the room) must match the room. The console exports only the messages it has loaded so far: our first download of the first run's room held the newest 2,500 of 10,005 messages; downloading again after the console had paged back to the start gave all of them.

Room hygiene between runs: never post into a room whose seats' workers are stopped (the messages queue and are delivered when the workers next start); remove seats from rooms they no longer need, because a seat's worker opens a session for every room it is a member of each time it starts; and keep earlier runs' repositories outside the seats' workspace.

## Evidence conventions

- Evidence block: item, unit, files changed, full commit id, exact commands from the repository root, output trimmed to the deciding lines, a "not covered" list, one known-bad probe that fails for the reason under test.
- Claim flags, per seat: the architect, critic and designer flag load-bearing statements VERIFIED, DERIVED or ASSUMED (a decision under uncertainty, with what would change it), and an ASSUMED statement never decides that a unit is complete; the verifier flags findings VERIFIED, VERIFIED-NEGATIVE (searched and found none, with the searching command), DERIVED or SUSPECTED (not reproduced; never blocks on its own); the release clerk reports only VERIFIED (run in this pass) or DERIVED; the builder's claims are its evidence block.
- Verdicts: item VERIFIED / REFUTED / UNVERIFIED (cause: evidence or environment); look APPROVED / CHANGES / UNVERIFIED; plan CLEAR / BLOCKED / SPLIT; gates PASS / FAIL / UNRUNNABLE.
- Board states: todo, in progress, handed back (marked blocked when it waits for an environment repair), verified, done. The architect is the only mover.
- Commits: every commit subject starts with the unit and item as the plan names them; a commit that answers a REFUTED, CHANGES or BLOCKED verdict says so in its body.
- The evidence record is one committed file in the repository, append-only within a unit; the verifier's checks and the design system live at the paths the plan names (ours: `acceptance/stage-N/` and `design/`).

## What we tried that failed, and what it changed

1. **The host machine's own Claude Code layer reached every seat** in the first three practice runs (the personal CLAUDE.md, rules, hooks and skill listings, VERIFIED from the seat transcripts). Fix: the clean configuration folder and per-seat launchers.
2. **Weaker models in gate seats.** A Sonnet-class clerk reported a false no-network PASS; a Sonnet-class builder fabricated a probe output. Fix: every seat on Opus 5.5.
3. **A provided check that could not fail.** In a practice run a provided concurrency check stayed green on a known-bad (a key recorded after a one-tick asynchronous yield); the verifier's own probe turned red on it. Fix: the verifier writes spec-derived checks and calibrates each one.
4. **A human accept step.** An early draft ended every unit with the human accepting it and sent a second split to the human. Fix: the final report ends a stage and splits are settled by rule.
5. **A report that never arrived (rehearsal, 2026-09-26).** The release clerk wrote its packaging report, but its long reverse-check command had been moved to a background task; the reply tool only stages a message until the turn ends, the turn ended on the background task's error, and the staged report was never posted. The clerk believed it had reported and nobody mentioned anybody for 35 minutes. In a hands-off run that ends the run. Fix: background tasks disabled in every launcher (known-bad VERIFIED), the no-background rule and the post-then-confirm delivery check in every mandate.
6. **A shared machine.** During the rehearsal a builder found the host port it wanted held by another project's container, which was redeployed by its own tooling minutes later. Fix: the never-touch rule in every mandate, a note in each task, and per-seat port ranges and container-name prefixes in the clerk's recipe.
7. **A generic first look.** A single-agent design draft (off-white surfaces, one muted accent, a stock sans) was rejected by the human as generic. Fix: the designer seat, rendered directions before one is chosen, and a mandate that names the generic default.
8. **Vendoring every dependency.** Our first build constraint required building with no network; the rule book allows the build to fetch dependencies and only the running service is offline. Dropped.
9. **Removing seats.** `jam rm` stopped each practice seat's worker but reported it "could not stop 1 of 1 runtime sessions"; the seats stay registered and count toward the 20-agent limit. We delete old seats in Band Desktop instead.
10. **The room filled up (first full run, stage 4).** Band stopped taking messages in the room at 10,000, and with every seat copying every tool call into the room, 7,810 of the 10,005 messages were tool-call copies. That happened 5 h 54 min into stage 4, with stage 4's items built and mostly verified: the builder's last fix handoff and the verifier's REFUTED verdict on one item never reached the room, and the stage has no final report. Nobody in the band or outside it was watching the count. Band staff had told us on 2026-09-27 that the per-room limit is there to protect users from runaway agents; on 2026-09-30 Band announced that some of its limit enforcement, room messages included, had not matched its free-tier plan limits and was fixed on the platform. We have not measured whether the 10,000 figure changed. Fix on our side either way: room activity per seat (four seats off), fewer and larger tool calls, handoffs in fewer parts, a watcher that reports the count; and a second full run in a fresh room.
11. **Old messages delivered by a restart (2026-09-29).** Test posts made days earlier to a practice room whose seats were stopped were delivered when Band Desktop restarted; one of them carried a full stage task, and the practice architect started planning it in the shared workspace until the operator stopped all workers. Fix: the room-hygiene rules under "Stand it up"; stale seats deleted before a run.
12. **The previous run's code next to the new one.** In that same incident the practice architect planned to "audit the existing stage-1" left in the workspace by the first run. A judged run must build its own code. Fix: earlier runs' repositories and task texts are moved out of the seats' workspace before a new run.
13. **The builder waited for every verdict (first full run).** One item at a time with no overlap left the builder without an active item for 289, 471, 339 and 89 minutes in stages 1 to 4. Fix: the next item is assigned at handoff and built on top of the handed-off commit; look review runs together with verification.
14. **A verdict count from memory.** The first run's stage-2 final report said the critic blocked two plan versions; the room shows one (the other was stage 1's). Fix: the final report takes every count from the plan's record.
15. **A departure announced in a handoff.** In stage 4 the builder knowingly departed from a DECIDED point and said so only in its handoff; the verifier refuted the item. Fix: a departure is asked about before it is built.
16. **A dropped finding.** A non-blocking stage-1 finding (the reset endpoint slowing by about 25 ms per seeded user, near its 10 s limit) was never taken up or recorded. Fix: every finding gets an owner and an outcome in the plan, and a measured breach of a stated limit is an item.
17. **A partial room export.** The Band console's "Download full session" first saved only the newest 2,500 of the room's 10,005 messages (its file still says "full"), and the organizers' offline check accepts that file, because it rejects only a filtered download (VERIFIED 2026-09-29 with the partial file as a known-bad). Fix: the count check in step 7 of "Stand it up".
18. **Watchers that never stopped (operator side, 2026-09-27).** On Windows, stopping a background watcher, by timeout or by hand, ended only its wrapper; the polling loop underneath kept running, and by morning 38 stale copies were running on the laptop, which ran hot and slow. Fix: one watcher (`factory/stage-watch.py`) that ends itself after 28 minutes and prints the stamp to resume from.
19. **A watcher filter that drifted (operator side, second run).** The watcher recognised verdicts by the band's message headers, and the seats' wording changed from stage to stage: "S3-I1 VERIFIED, ...", a refutation inside another item's verdict, a leading "@owner/seat" handle, "**Verdict: VERIFIED.**" after a long header. It missed verdicts five times; the final reports were always caught, and no dispatch waited on a missed line. Fix: match the upper-case verdict words anywhere in the first 800 characters of a message except handoff parts, and replay the filter over the room's messages at every stage boundary (the replay is how each miss was found).
20. **A general error rule not carried to new endpoints (second run, found after it by the operator's audit).** Stage 1's error table reserves 400 `malformed_request` for a field of the wrong JSON type. The band applied it on the stage-1 endpoints but sent every field problem on the endpoints added in stages 3 and 4 to 422. Where a stage's text overrides the table for that endpoint (policies, series counts, amendments) that is right; but a wrong-typed `table_id` on the replan preview, and a wrong-typed `anchor_reference` on series adoption, answer 422 where the table says 400 (reproduced on the delivered image). The architect had listed its field-error order among the decisions a held-back check could contradict, and the verifier's checks encoded the decision instead of the table. A stage counts when it passes at least half of each suite, so this cannot cost a stage. Fix for the next run: a new endpoint inherits the stage-1 error table unless its own stage's text says otherwise, and a decision that departs from a general rule quotes the sentence that allows it.

## Risks carried into the run

1. **A silent stall.** A seat whose runtime dies, or whose turn fails on a usage limit mid-stage, wakes nobody; the architect's 60-minute re-send covers a seat that is alive but quiet, not a dead runtime. A crashed seat means the run is repeated from scratch in a fresh room (the organizers' answer).
2. **Verification time.** Calibrating every spec-derived check is slow: 61 % of the first run's wall-clock time was verification. The overlap of building and verifying recovers idle time, not verification time.
3. **Docker on the host.** Gate 1 needs Docker; if it cannot run, the clerk reports gate 1 UNRUNNABLE, the honest state.
4. **Room size.** About 5,400 messages were projected and the run used 3,260 (the first run's room stopped at 10,000, failure 10); the watcher reports the count, and above 8,000 the operator can set the builder and the designer to `off` too (a Band setting, not a message in the room).
5. **A restart of Band Desktop mid-run** restarts every seat's worker and delivers anything queued; the operator does not restart it during a run.
